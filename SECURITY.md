# Security Policy

## Reporting a Vulnerability

If you discover a security vulnerability in kyverno-in-action, please **do not** open a public GitHub issue. Instead, please report it responsibly by emailing [23seriy@gmail.com](mailto:23seriy@gmail.com) with:

- A description of the vulnerability
- Steps to reproduce it
- Potential impact
- Any suggested fixes (if you have them)

**Please do not disclose the vulnerability publicly until we've had time to address it.**

We will:
1. Acknowledge receipt of your report within 48 hours
2. Provide a timeline for a fix
3. Work with you on the patch if needed
4. Coordinate a disclosure date with you
5. Credit you in the security advisory (unless you prefer anonymity)

## Scope

This security policy covers the kyverno-in-action repository itself. It does **not** cover:

- **Kyverno itself** — please report Kyverno vulnerabilities to the [Kyverno project](https://github.com/kyverno/kyverno/security)
- **Kubernetes** — please report Kubernetes vulnerabilities through their [security disclosure process](https://kubernetes.io/security/)
- **Cosign** — please report Cosign vulnerabilities to the [Sigstore project](https://sigstore.dev/)

## What We Fix

We consider the following as potential security issues:

- **Code injection** in scripts (shell, Python)
- **Insecure cryptographic practices** (especially in the Cosign workflow)
- **Unintended credential leakage** (e.g., keys in git history)
- **Unsafe defaults** that could allow unintended policy bypasses
- **Supply chain risks** in the build and image signing workflow

We do **not** consider the following as security issues (please file them as bugs instead):

- Demo scenarios that intentionally violate policies (the point of this project)
- Kyverno policy misconfigurations (report to Kyverno)
- Kubernetes API vulnerabilities (report to Kubernetes)

## Security Best Practices When Using This Project

### For Demo/Learning Environments

- **Use Minikube, not production clusters** — this project is a demo, not a production-hardened system
- **Run in isolated networks** — don't expose the Minikube cluster to the internet
- **Regenerate Cosign keys** — the keys in `cosign/` are for demo purposes only; never use them in production
- **Clean up after demos** — run `./scripts/05-teardown.sh` to delete the test cluster

### For Extending to Production

If you're using this project as a blueprint for production policies:

- **Review all policies** — ensure they match your organization's security requirements
- **Use your own image registry** — not the in-cluster registry
- **Implement signed image verification** — use your own Cosign or Sigstore setup
- **Add comprehensive logging** — monitor Kyverno webhook decisions
- **Test thoroughly** — run policies against real workloads in a staging environment before production
- **Keep Kyverno updated** — regularly update to the latest Kyverno patch version

## Known Security Considerations

### Cosign Signing in This Project

The Cosign keypair generated by `scripts/03-deploy-app.sh` is:
- Stored locally in `cosign/` (gitignored)
- **Not password-protected** — suitable for demos only
- **Intentionally unsigned public key embedded in policies** — for simplicity in a demo

For production, use:
- A proper secrets management system (Vault, AWS Secrets Manager, etc.)
- Keyless signing via OIDC
- Proper audit logging of all signing operations

### Registry Access in This Project

The in-cluster registry used by this demo:
- Is **HTTP only** (not TLS)
- Has **no authentication**
- Is accessible from inside the cluster only (Minikube port-forward)

This is fine for learning; production registries must use TLS and authentication.
